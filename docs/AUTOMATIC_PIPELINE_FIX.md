# 第三步“一键生成新签名”流程适配（2026-11-01）

## 此次代码定位到的问题

1. `keygen._check_config` 仍有 100 字符名称上限。A 的姓名、机构、`@` 标识拼接后可能超过该上限，虽然主体构造层已有长 CN 兼容，仍会在预检被提前拒绝。已删除这个产品长度上限，不截短用户名称。
2. 主按钮以前等待 A 卡片缓存完成，再打开强制确认窗口；它不是直接运行生成流水线。新流程不依赖界面缓存，按钮直接提交后台完整操作。参数窗口改成“选择 / 生成证书 → 调整自动生成参数…”中的可选入口。
3. `request_signature_reads` 每次刷新都重新启动同一个单次计时器。改为已有计时器运行时不重置；排队生成也不反复重启读取调度。
4. 参数窗口原来把后台忙碌和文档变化混为一谈，要求重新打开窗口。现在窗口期间暂停尚未开始的自动读取，不再用该忙碌判断中断确认。
5. 模板构造/启动异常未在按钮槽函数内处理，pythonw 场景可能只写入不可见 stderr。现在显示实际异常及失败工序。
6. 主体无 CN 时，新补加 CN 的分支未复用长名称兼容代码。现有和新补 CN 共用同一编码处理。

上述是源码中确认存在的问题/触发条件；本次未取得用户失败当次的异常堆栈，不能断言那个案例具体由哪一条触发。

## 新入口及数据工序

`qt_workbench_shell.WorkbenchShell.generate_b_signature`
→ `qt_automatic_signing.start_automatic_b_signing`
→ `automatic_pipeline.generate_b_from_original`
→ 既有 `automatic_signing.generate_and_sign_b`
→ 共用 `_complete_generated_b`。

1. 主线程冻结当前 A/B 路径、文件标识和 A 的选中签名字段；控件仅提供字段定位，不能作为证书来源。
2. 工作线程对实际 A 原文件调用 `read_signature_audit(..., allow_network=False)`。A 没有签名/读取不完整不作为生成许可门槛；无法读取时明确报告并使用默认参数。
3. `generation_reference` 从 A 的实际报告选出签名并深拷贝。`build_reference_template` 提取主体属性、名称前段、密钥规格和摘要算法，保留界面中已生成且对应同一原始字段的新标识。
4. 新私钥、新公钥、新自签证书、证书序列号及实际 CMS 签名由程序生成，不复制 A 的公钥/签名值作为 B 的生成结果。
5. 输入始终是当前累计修改后的 B，不重新从 A 生成正文。输出独立命名，自动避开已存在文件。
6. 签署并关闭输出后，重读最终 B。A/B 使用同一个读取/检查函数，报告分别绑定各自实际文件标识。
7. UI 回填 A 的原稿实际报告和 B 的最终文件实际报告，以生成证书指纹定位新签名。失败显示工序和原始错误，不把失败改为通过。
8. 可选参数窗口也使用同一流水线，只覆盖用户确实修改过的参数，不让旧控件默认值盖掉后台读取到的 A 参数。

## 保留的文件/技术行为

- A 和已有 B/密钥不覆盖；不上传，不联网检查。
- 读取失败、密码/文件错误继续显示；加密库的实际编码错误不伪装成功。
- 新证书是本机生成的自签证书；A 的签发方签名不可能通过复制可见字段而变成新证书的实际签发签名。该事实不作为禁止 B 签署的条件。
- 生成已在执行时不重复提交另一套凭据；其他任务忙碌时保存首次点击，结束后自动执行。
- 执行阶段只写入既有界面日志；不在 PDF 旁新增修改记录，不记录密码或私钥内容。
- 本次没有删除所有错误处理、源文件保护或证书验证结果；只移除上述误阻断并接好完整工序。

## 本轮检查边界

按用户此前“不需要验证”的要求，仅做 Python 语法编译、模块导入、静态调用顺序/按钮接线、安装 SHA 核对。新增虚构数据回归用例，但不运行 pytest、不启动或重启 GUI、不生成真实密钥、不实际签署用户文件。

因此，源码和安装结果可以确认；真实签署与界面验收本轮未执行。运行中的旧进程需由用户保存当前工作后重新打开“qpdf Studio 最新版”加载本次代码。
