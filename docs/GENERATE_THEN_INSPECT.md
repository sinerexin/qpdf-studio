# 第三步：先生成真实 B，再读取和检查

## 用户确认的流程

- A 原稿：只读解析、检查、显示，不改原文件。
- 生成参考：从 A 实际报告取用户选定签名的名称/主体属性、算法规格和摘要算法，保留可调整参数。
- B：以第二步累计内容为源，生成独立新密钥对、自签证书和 PDF 数字签名，完成输出文件。
- 生成结束后重新打开输出 B，调用和 A 相同的 `read_signature_audit`，再显示实际签名、证书、公钥和验证结果。
- 两边共用检测与显示格式。第三步自动流程下，B 未生成时显示“待生成后检查”，不把旧签名失效当成新签名的结果；人工验签入口仍可单独检查文件。

## 本轮确认并修复的错误

界面文件标识已有六项（路径、长度、修改时间、创建/变更时间、设备、文件号），自动生成函数仍构造三项元组并严格比较。
这会使未变化的同一 B 也被误报“文件已变化”。新 `file_identity.py` 为界面、后台预检及回调提供同一六项格式。
这是调用契约修复，没有增加身份、证书来源、CA 或编辑门槛。

## 修改内容（均有中文注释）

- `automatic_signing.py::generation_reference`：从 A 实际报告复制参数快照，不反向读取格式化标签或 B 显示模板；不改原报告。
- `generate_and_sign_b`：生成凭据 → 签署实际 B → 等输出关闭 → 重新读取最终文件 → 返回实际报告，顺序明确。
- 后台使用现有 `read_signature_audit`，与 A 相同的解析、摘要、数学签名和信任检查逻辑，不为 B 构造另一套“通过”标准。
- 本次签名按最终 PDF 内证书 SHA-256 与本次新证书指纹关联；默认展示本次签名，而不是猜测第一个或最后一个对象。历史签名仍可逐个查看。
- `qt_automatic_signing.py`：只有生成后报告可进入 B 缓存；生成参数和 credential_summary 不充当验签报告。
- `qt_workbench_shell.py`：生成请求在 A 尚未读完时排队接续；A 无签名仍可使用默认参数生成。离开第三步或更换文档不再弹出旧请求的生成窗口。
- `qt_signature_evidence.py`：B 生成前使用中性待检查状态；不显示预先推测的通过/失败。
- 检查失败保留已生成 PDF 与凭据，显示实际读取错误，不删除产物、不伪造通过；可用现有重新读取/人工验签功能重试。
- 程序自动配置凭据密码的既有流程未改变；密码、私钥不进入返回报告或日志。
- 未改第二步累计和跳转逻辑，未写 PDF 旁修改记录，未覆盖 A 或第二步 B。

## 实际检查范围

新增/更新回归定义，覆盖文件标识一致、生成后重读顺序、原数据不变、实际失败保留、证书指纹关联、A 读取等待、B 生成前后检查时机。
沿用用户此前“不需要验证”：未运行 pytest、未启动 GUI、未生成真实密钥、未签署任何真实或教学 PDF。
本轮仅语法、导入、静态接线与安装 SHA 核对；不将它们表述成功能验收。
退出旧进程后，从桌面“qpdf Studio 最新版”重新打开才会加载新代码。
