# A/B 签名数据与显示路由修正

## 已确认的代码问题

1. `WorkbenchShell.update_signature` 将全局 `w._signature_audit` 按刷新时的 active_slot 写回缓存，还会按字段名拼接旧 full_evidence。显示函数因此具备修改另一侧报告的能力，而不是只读投影。
2. B 无真实签名条目时，`SignatureInformationPane._render_tab` 用 A 模板的 `preview_entry/preview_audit` 填信息卡。模板继承 A 的证书、公钥、ByteRange、CMS 长度，可能与 B 实际验证结果相互矛盾，即使旁边已有模板说明也容易误读。
3. A 默认选择第一项签名，B 默认选择最后一项；同一多签名文件可能展示不同签名对象，并非采用不同摘要算法。
4. 加载新文件时先清缓存、后绑定路径，导致清理刷新短暂仍指向旧文件。
5. 人工验签回调只比较文件路径；A/B 同路径且用户切侧时，也可能继续写当前显示。
6. 旧摘要面板在字段验签数量为零、但对象扫描实际发现签名数据时，仍可能显示“没有数字签名”。

## 本次修改及中文注释

- `qt_workbench_shell.py`：显示函数仅读当前侧有效缓存，不再写缓存或拼接其他报告。点击行仅接受当前报告内的原始行；摘要跟随当前签名选择。
- 缓存文件标识增加文件标识号、设备与创建/变更时间，用于发现同路径替换；这不是用元数据替代密码学摘要。
- `qt_desktop.py`：先绑定真实新路径，再清理该侧报告；人工回调同时核对原始栏位与文件路径，结果只归属任务开始时的 A 或 B。
- `signature_card_data.py`：共用默认选择规则（保留用户选择，否则优先最新字段签名，最后才是扫描候选）；提供实际读取路径、大小和文件 SHA-256 的只读显示数据。
- `qt_signature_evidence.py`：A/B 使用相同选择规则；文件提示、信息详情和验证详情展示后台实际文件来源与 SHA-256。
- `qt_signature_cards.py`：A 参考模板保留给生成配置和独立参考详情，但不再填入 B 的“实际签名/证书/公钥”卡片；生成新凭据仍单独标注为待用。
- 未新增证书来源、CA 或身份门槛；未修改签名、密钥生成能力，未将任何失败强制改成通过。
- 没有修改第二步累计预览及确认进入第三步的接线，没有重写、复制或上传原 PDF，没有写 PDF 旁的修改记录文件。

## 对用户判断的核对

当前摘要补充检查确实按实际磁盘 ByteRange 读取字节；既有名称分段函数生成新显示对象，没有修改 PDF 或原报告。
本次修复针对实际发现的显示/缓存/对象选择混用，不能据此认定某份 A 的签名一定有效、某份 B 的字节未变化。
内容流修改和原证书仍然存在是两件事；具体检查结果只以当前实际文件报告为准。
